# BRC-208: Vault Sub-Accounts

Brandon Cryderman (brandongcryderman@gmail.com)

## Abstract

This standard defines how a wallet derives any number of additional **account roots** from the root key it already holds. Account 0 is that root key, unchanged. Account `n ≥ 1` is the [BRC-42](../key-derivation/0042.md) child of the root under the protocol `[2, "account"]`, key ID `account-n`, and counterparty `self`. Each account is a complete [BRC-100](./0100.md) wallet with its own identity key, outputs, and history. Restoring the root key alone recovers every account: the wallet rediscovers them by index, with no account list to back up. The account protocol is reserved for the wallet, in the manner of [BRC-44](../key-derivation/0044.md), so that applications can never obtain an account key, a signature by one, or the linkage between accounts.

## Motivation

People want separate on-chain identities for separate purposes, such as a personal wallet, a shop, an issuer and a website, without keeping a separate seed phrase for each one. Many deployed wallets hold a single root private key and treat it as the BRC-100 root:

- a [BRC-75](../key-derivation/0075.md) key, which is SHA-256 of the BIP-39 seed;
- a key recovered from an older HD wallet;
- a raw private key imported without any mnemonic.

[BRC-157](../key-derivation/0157.md) profiles (`m/0'/i'`) solve the same problem for entropy-rooted wallets, but they cannot serve these wallets:

- They need the BIP-32 master node, which an imported root key does not have.
- Their profile 0 is `m/0'/0'`, which is not the root such a wallet already holds, so adopting them means moving every existing coin and identity.

This standard derives accounts from the root key itself. Existing wallets become account 0 with no migration, and every additional account is recoverable from whatever already recovers the root.

## Specification

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" are to be interpreted as described in RFC 2119.

### Vault root

The **vault root** is the wallet's root private key: the key whose public key is the wallet's BRC-100 identity key before any account exists. This standard does not constrain how the vault root was produced.

### Account roots

Account `0` is the vault root. Implementations MUST NOT derive account 0, and MUST NOT change the vault root when accounts are added.

For an integer `n ≥ 1`, the account root is the BRC-42 child of the vault root, derived with the [BRC-43](../key-derivation/0043.md) invoice number `2-account-account-n`:

| Field | Value |
|---|---|
| Security level | `2` |
| Protocol name | `account` |
| Key ID | `account-n` in decimal, with no leading zeros (`account-1`, `account-2`, …) |
| Counterparty | `self` |

In the BSV TypeScript SDK:

```ts
const accountRoot = new KeyDeriver(vaultRoot)
  .derivePrivateKey([2, 'account'], `account-${n}`, 'self')
```

An account root is a secp256k1 private key like the vault root, and signs with ECDSA. The account's identity key is the compressed public key of its account root. From then on the account root is an ordinary BRC-100 root key. Every key the wallet derives for that account, including its baskets, its certificates and any BAP identity, is derived from the account root alone. Accounts do not share outputs, actions or permissions.

### Reserved protocol

The protocol name `account` is reserved for the wallet at every security level, as BRC-44 reserves names beginning with `admin`. A wallet implementing this standard:

1. MUST refuse every application request whose `protocolID` names `account`. The name is compared after the BRC-43 normalisation (lowercase, surrounding whitespace removed). This covers `getPublicKey`, `createSignature`, `verifySignature`, `encrypt`, `decrypt`, `createHmac`, `verifyHmac`, and `revealSpecificKeyLinkage`.
2. MUST refuse `revealCounterpartyKeyLinkage` and `revealSpecificKeyLinkage` when the counterparty is the wallet's own identity key or `self`, under any protocol. Counterparty linkage with itself yields the BRC-42 offset of every `self` child, and specific linkage yields one child's offset. A `self` child is the root plus its offset, so an offset together with that child's private key gives up the root. Any key the wallet exports as a `self` child (an account root, a server key, a BAP signing key) is enough for that.
3. MUST refuse these requests without a permission prompt. A user cannot meaningfully consent to handing out another account's key.

Without rule 1, an application approved on account 0 could ask for a signature by `[2, "account"]`, `account-1`, `self` over a transaction sighash and spend account 1. Rule 1 also blocks the weaker leaks: it stops the application linking account identity keys to one vault through `getPublicKey`.

### Allocation and naming

Implementations MUST allocate indices in order, starting at 1. A new account takes one more than the highest index ever allocated under the vault root. An index is its key: implementations MUST NOT reassign an index to a different account, including after the user hides or archives one. After recovery, the highest discovered index counts as the highest allocated. An index allocated before recovery but never used holds no state, so handing it out again is harmless.

Account names are local metadata. They MUST NOT affect derivation. A wallet SHOULD keep `{ index, name, identityKey }` for each account, keyed by the vault root's identity key.

### Recovery

The vault root alone MUST be sufficient to recover every account. No account list, name or other backup may be required to find an account or derive its keys.

1. Recover the vault root by its usual means (BRC-75 mnemonic, BRC-157 backup, imported key). This is account 0.
2. **Discover** the accounts. Starting at index 1, derive each account's identity key in order and check it for use: any record the wallet would itself rely on to recover that account. Examples are a history backup stored for the identity key, or messages waiting for it at its messagebox. Requests to those hosts are signed by the candidate account's own root key, so no host learns any key.
   - An index is **used** when a record exists, and **unused** when every source answers that none does.
   - A wallet MUST NOT stop before five consecutive unused indices. Every index up to the highest used one is an allocated account, because allocation is sequential.
   - When a source cannot answer, the wallet MUST NOT treat the index as unused. It keeps the accounts found so far and resumes discovery from that index later.
3. Derive each account root as above and open it as its own wallet. An account that opens with empty local state recovers its history exactly as the vault root's own wallet does (for example, from its history backup), then reconciles with the chain.

Account names are not recoverable from the vault root. A wallet MAY back them up beside each account's state; otherwise discovered accounts take default names.

### Choosing between this standard and BRC-157 profiles

A wallet whose root is a BRC-157 root key MAY use either scheme. For one vault root it MUST use one scheme only and record which one, so recovery derives the same accounts. Wallets whose root is not a BRC-157 root key use this standard.

## Security considerations

- **The vault root controls every account.** Anyone who holds it holds them all. That is the purpose of one backup and one unlock, and wallets SHOULD say so where accounts are created.
- **An account key is not independent of the vault.** Account root `n` is the vault root plus a BRC-42 offset, and only the vault root can compute that offset. One exported account key plus that offset reveals the vault root. The reserved-protocol rules exist to keep the offset unreachable. A wallet that exports an account key MUST NOT describe it as isolated from the vault.
- **Rotation.**
  - *Account roots cannot be rotated in place.* An account whose key is exposed is retired: its funds move to a new index, and the old index stays allocated (discovery still finds it).
  - *Rotating the vault root replaces every account.* A wallet that does so must move each account's value and identities to the new root's accounts; nothing carries over automatically.
  - *Keys under an account root rotate independently of this standard*, for example a BAP signing key moving from `identity-N` to `identity-N+1`. But rotation does not change a retired key's offset: an old exported key plus its offset still gives up the account root. That is why rule 2 refuses linkage outright rather than per key.
- **Signing.** Account roots sign with ECDSA. Nonces MUST be deterministic per RFC 6979, keyed by the signing key and message, as the BSV SDKs already do; BRC-100 offers no caller-supplied nonce. The vault root and its account roots are related keys, but each draws its nonces from its own key, so no two of them share one.
- **Discovery is visible to the hosts it queries.** A host asked about several identity keys from one client in a short time can infer that they share a vault. Wallets SHOULD probe only hosts the user already relies on for those accounts, and only during recovery.
- **Accounts are unlinkable to outsiders.** BRC-42 children of `self` look like unrelated public keys. The account protocol is reserved, so no application can obtain the linkage, and the wallet MUST NOT disclose which accounts share a vault to an application.

## Rationale

- **Why not BRC-157 profiles for every wallet?** They need the BIP-32 master node, and they would replace the root that existing wallets already use. Deriving from the root key keeps account 0 exactly where it was.
- **Why a BRC-42 child of `self` and not a new KDF?** Every BRC-100 wallet already implements the derivation, it needs no new primitive, and the invoice number cannot collide with any other protocol. BRC-43 names contain no hyphens, so `2-account-account-n` arises only from this protocol.
- **Why `account` and not a name under BRC-44's `admin` prefix?** The derivation was deployed before this specification. Changing the name would move every deployed account root and strand its coins. Reserving the name explicitly gives the same protection.

## Non-goals

- Moving value between accounts. A transfer between accounts is an ordinary payment.
- A second identity hierarchy. Each account's identity is its account root, and BAP, certificates and handles attach to it exactly as they would to any BRC-100 root.
- Same-identity device synchronisation. Each account syncs and backs up like any other wallet.

## Implementations

- HandCash Desktop and Mobile derive and switch accounts with this protocol, and refuse the reserved requests at their BRC-100 bridge. Account 0 keeps its historical wallet database; account `n ≥ 1` uses a database with an `-a<n>` suffix.
- After unlock, HandCash discovers accounts the device does not list. It checks each candidate for a history backup and for waiting messagebox mail, signing as that account. An account that opens empty restores from its own history backup before reconciling with the chain.
