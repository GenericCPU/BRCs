# BRC-250: Email Login for BRC-140 Share Vaults

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

## Abstract

This BRC lets a user sign in to a self-custodial wallet on a new device with their email, the way they sign in to any app, without any operator being able to take the wallet.

Signing in on a new device means getting the vault master onto it. The master is split with [BRC-140](../key-derivation/0140.md), and independent [BRC-154](./0154.md) backup services each hold one share. A holder releases its share to a new device only when all of these are true:

1. **The host is validated.** The login was started through the pinned host, `handcash.io`. Its published key signed a one-time identifier naming a key only the new device holds.
2. **The email is validated, in zero knowledge.** The new device presents a zero-knowledge proof, bound to that identifier, for the email enrolled with this wallet. The email itself is never revealed to the holders. There are two ways to make the proof:
   - **Any email address:** the user sends one email to the host's sign-in address on `handcash.io`. The proof shows the user's own provider signed it (DKIM) and that it went to that address.
   - **Google accounts, in one tap:** the proof shows Google signed a sign-in token for HandCash's app at `handcash.io`.
3. **The login is approved or has waited.** Either one of the user's signed-in devices approves it, or it has waited seven days without being refused.

Holders track which signed-in devices have been online in the last seven days. If any have, the new device asks them to approve and shows which ones. If none have, it tells the user when the login will be ready.

No proof works outside one login on one device, through a host and holders fixed at enrollment. No proof completes a login without a device's approval or the full wait.

## Motivation

Users expect to sign in with their email. Wallets that allow it usually let the operator check the email, which makes the operator a custodian: whoever runs the check, or breaks into it, can sign in as anyone. An operator-sent one-time code is a check the operator can pass on its own.

Two signatures the wallet operator cannot produce already prove an email:
- **DKIM.** Every major mail provider DKIM-signs the mail its users send: the sender, the recipient and the headers.
- **Google ID tokens.** Google signs an OpenID Connect ID token naming the app it was issued to and the verified email.

A zero-knowledge proof over either lets independent holders check the signature, the host and the binding without learning the email.

The email alone still must not be enough, because an inbox can be stolen. People who sign in on a new device almost always have another one nearby, so the other device approves. Someone who has lost every device waits seven days, during which any device that comes back online, or the inbox itself, can refuse.

## Terminology

| Term | Meaning |
|---|---|
| Vault master | The secret a new device needs, for example BRC-157 entropy. |
| Signed-in device | An install holding the vault master. |
| New device | The install signing in. |
| Host | `handcash.io`. It publishes the attester key, its sign-in mail address and the app's Google client ids. |
| Attester | The host's login service. It signs identifiers and sends notices. It holds no share unless it is also a holder. |
| Holder | A BRC-154 backup service holding one share, run by an operator independent of the other holders. |
| Login key | A fresh secp256k1 key the new device generates for one login. Released shares are sealed to it. |
| Identifier | The attester-signed statement naming the account, the holders and the login key. Its hash is the **binding**. |
| Email proof | A zero-knowledge proof over a DKIM-signed email the user sent to the host (`email-zk`), or over a Google ID token (`oauth-zk`). |
| Email commitment | `Poseidon(email, salt)`. The only form of the email a holder stores or sees. |
| Device authority key | A key every signed-in device can derive from the vault and nothing else can. It signs presence, approvals and refusals. |
| Login request | A holder's record of one pending login. |

## Specification

### Host manifest

The host publishes `https://handcash.io/.well-known/brc250.json`:

```json
{
  "v": 1,
  "attesterKey": "<compressed public key>",
  "loginMailbox": { "localPart": "login", "domain": "handcash.io" },
  "googleClientIds": ["<native client id>", "…"],
  "circuits": {
    "email-zk": { "id": "<SHA-256 of the Groth16 verifying key, hex>", "url": "<where the key is published>" },
    "oauth-zk": { "id": "<…>", "url": "<…>" }
  }
}
```

- `loginMailbox` is where users send their sign-in email. The host's domain MUST accept mail for `<localPart>+<anything>@<domain>`.
- The `googleClientIds` are native-app OAuth clients registered by the host's verified `handcash.io` domain. Google redirects them only to app-owned addresses.

A wallet fetches the manifest over TLS at enrollment and pins its contents. The pinned copy changes only through a re-enrollment from a signed-in device.

### Device authority key

Every signed-in device derives the same device authority key. It is the [BRC-42](../key-derivation/0042.md) child of account 0's identity key for protocol `[2, "brc250 device"]`, key id `1`, counterparty `self`. Only a device holding the vault master can produce it. A device that can sign with it already holds the wallet, so it gains nothing by approving a login it should not.

Each install also keeps a random `deviceId` and a human label such as `MacBook · Desktop`.

### Enrollment

The first device enrolls when the wallet is created, or when the user turns on email login:

1. It splits the vault master with BRC-140. It sends one share to each of at least two holders and keeps at least one share off every holder (an offline slice the user saves).
   - The holders together MUST reach the threshold, so email login can complete.
   - No single holder may reach it.
2. It picks a random 31-byte `salt`, obtains an identifier with purpose `enroll`, and completes an email proof for it. The email is proven before it is stored, because a mistyped address would lock the user out.
3. It sends each holder, with BRC-154 `POST /share/enroll`:

```json
{
  "share": "<BRC-140 share>",
  "identifier": { "…": "purpose enroll" },
  "emailProof": { "…": "see Email proof" },
  "salt": "<hex>",
  "deviceAuthorityKey": "<compressed public key>",
  "fastKey": "<compressed public key, optional>",
  "waitSec": 604800,
  "manifest": { "…": "the pinned host manifest" },
  "holders": ["https://holder-a.example", "https://holder-b.example"],
  "device": { "deviceId": "<hex>", "label": "<text>" },
  "reenrollSignature": "<only when a record exists; by its device authority key>"
}
```

The holder verifies the identifier, which must have purpose `enroll`, and the email proof. Each holder keeps one record per `accountRef`.

If a record already exists, the request MUST carry `reenrollSignature`, signed by the existing record's device authority key over `brc250-reenroll\n<binding>`. Otherwise the holder refuses it. A HandCash session alone can never replace a record, its email, its pinned manifest or its holders.

The holder then stores:
- the share, encrypted at rest;
- the identifier's `accountRef`, the email commitment from the proof, and the salt;
- the device authority key and the fast key;
- the wait;
- the pinned manifest and the holder set;
- the device in its device list, seen now.

`waitSec` MUST be at least 604800 (seven days). A holder MUST refuse to shorten it.

The fast key is the public key of `HMAC-SHA256(key = offline share string, data = "brc250-fast\n" + holder origin)` read as a private key. A request signed by it proves the new device holds the offline slice, and reveals nothing about that slice.

The attester MAY issue a [BRC-52](../peer-to-peer/0052.md) certificate binding the account to account 0's identity key. The vault master itself never signs (BRC-157).

### Presence

While unlocked and online, each signed-in device tells each holder it is alive, at most once an hour and at least once a day:

```json
POST /presence
{
  "deviceId": "<hex>",
  "label": "<text>",
  "state": "active" | "signedOut",
  "at": <unix seconds>,
  "signature": "<compact ECDSA by the device authority key, hex>"
}
```

The signature covers `brc250-presence\n<deviceId>\n<label>\n<state>\n<at>`. A holder MUST refuse an `at` more than five minutes from its clock, or not newer than the device's last one. It records `lastSeen` per device. When a device signs out (the wallet is wiped from it), it sends `signedOut` and the holder drops it.

A device is **recent** if its `lastSeen` is within the last seven days. Presence is sent only while unlocked, so a locked or stolen device stops counting after seven days.

### Identifier

The new device generates a login key `L` and signs in to the attester (HandCash: the account and login the user already has on the market). The attester returns an identifier for that signed-in account, and never for an account or email the client names:

```json
{
  "v": 1,
  "purpose": "login" | "enroll",
  "accountRef": "<hex SHA-256 of \"brc250-account\\n\" + the host's account id>",
  "loginKey": "<L, compressed hex>",
  "holders": ["https://holder-a.example", "https://holder-b.example"],
  "context": "<what the attester saw: client type and approximate location>",
  "refuseHash": "<hex SHA-256 of a refuse code the attester emails to the account>",
  "iat": <unix seconds>,
  "exp": <unix seconds, at most iat + 900>,
  "nonce": "<16 random bytes, hex>",
  "signature": "<64-byte compact ECDSA, hex>"
}
```

The preimage is these lines joined with `\n`. Holders are sorted and joined with `,`. `context` is UTF-8 with no line breaks, at most 200 bytes.

```
brc250-identifier
v1
<purpose>
<accountRef>
<loginKey>
<holders>
<context>
<refuseHash>
<iat>
<exp>
<nonce>
```

`signature` is by the pinned attester key over SHA-256 of the preimage. The **binding** is the base64url SHA-256 of the preimage, without padding.

The **match number** is `uint16(SHA-256("brc250-match\n" + binding)[0..2]) mod 100`. It is printed as two digits.

For every identifier it issues, the attester MUST email the account's address: "Someone is signing in to your wallet on `<context>`". The email carries:
- a link with the refuse code;
- `Reply-To: <localPart>+<binding>@<domain>`;
- the line "Reply only if you are signing in on that device right now and it shows <match number>".

Replying is the `email-zk` sign-in.

### Email proof

Both methods produce a Groth16 proof under the circuit the pinned manifest names for that method. Strings in public signals are packed into BN254 field elements, 31 bytes each, big-endian. The email commitment is `Poseidon(lowercase(email address), salt)`.

The device SHOULD prove locally, logging `[email-login] prove done <N>ms`. It MAY use a proving service. That service learns the email, but what it sees only works for this binding, and the binding names `L`, so it can do nothing with it.

To compute the commitment, the device needs the salt. A holder returns it from `POST /login/salt`, but only for a valid identifier from the pinned attester whose `accountRef` matches a record. Without a signed-in HandCash session, nobody can learn the salt and test guessed emails against the commitment.

#### `email-zk`: any email address

**Sending.** The user sends one email from the enrolled address to `<localPart>+<binding>@<domain>`, for example `login+3q2-…@handcash.io`. They do it either way:
- by replying to the attester's notice, whose `Reply-To` is that address;
- through a pre-filled `mailto:` the new device opens.

The subject and body do not matter.

**Collecting.** The host's inbound mail service keeps the raw message for the identifier's lifetime. The new device fetches it with its HandCash session. The host sees the message, but it cannot alter it without breaking the signature, and it cannot produce one.

**The circuit** proves, for the private signed header block and a private salt:
1. A `DKIM-Signature` (`a=rsa-sha256`) over the relaxed-canonicalized signed headers verifies under an RSA modulus of at least 2048 bits, whose Poseidon hash is the public `dkimKeyHash`.
2. The signature's `d=` and `s=` equal the public `dkimDomain` and `selector`.
3. Its `h=` list includes `from` and `to`.
4. The `From` address's domain equals `dkimDomain` or is a subdomain of it (aligned), and that address is the one in the commitment.
5. The `To` header contains exactly the public `toAddress`.
6. The public `emailCommitment` is as defined above.

Public signals, in order: `dkimKeyHash`, `dkimDomain`, `selector`, `toAddress`, `emailCommitment`.

The body is not proven, so the proof works for any reply.

**A holder MUST check:**
- that the proof verifies under the pinned `email-zk` circuit;
- that the key published at `<selector>._domainkey.<dkimDomain>` hashes to `dkimKeyHash`. The key MUST be fetched over DNSSEC, or from at least two independent DNS-over-HTTPS resolvers that agree;
- that `toAddress` is `<localPart>+<binding>@<domain>` from the pinned manifest. That one check validates both the host and the binding;
- that the identifier has not expired. The binding did not exist before the identifier was issued, so the message is fresh;
- that `emailCommitment` equals the record's commitment.

`dkimDomain` reveals the user's mail provider (for example `gmail.com`), but not the address.

#### `oauth-zk`: Google accounts

**Obtaining the token.** The new device obtains a Google ID token whose `nonce` claim is the binding. It MUST obtain it itself:
- with the authorization code flow and PKCE ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636));
- through a redirect only that app can receive ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)): a loopback address on desktop, a verified app link on mobile;
- with a code verifier and `state` that exist only in the process holding `L`.

It MUST NOT use a web redirect through the host or any other server, the device authorization flow, or a token pasted in by the user. If someone else's browser completes the Google sign-in, the code lands on that machine. If a website completes it, the code lands nowhere. The app that started the login never receives it.

**The circuit** proves, for a private token and a private salt:

1. The token's RS256 signature verifies under an RSA modulus whose Poseidon hash is the public `googleKeyHash`.
2. Its claims are well-formed, and:
   - `iss` is `https://accounts.google.com`;
   - `aud` equals the public `aud`;
   - `nonce` equals the public `nonce`;
   - `exp` equals the public `exp`;
   - `email_verified` is `true`.
3. The public `emailCommitment` is as defined above, over the `email` claim.

Public signals, in order: `googleKeyHash`, `aud`, `nonce`, `exp`, `emailCommitment`.

**A holder MUST check:**
- that the proof verifies under the pinned `oauth-zk` circuit;
- that `googleKeyHash` matches a key in Google's published key set (`https://www.googleapis.com/oauth2/v3/certs`), current or retired within the last 24 hours;
- that `aud` is one of the pinned manifest's `googleClientIds`, so the token was issued to the `handcash.io` app (the host);
- that `nonce` equals the binding;
- that `exp` has not passed;
- that `emailCommitment` equals the record's commitment (the email).

#### Which method, and what neither does

The new device offers `oauth-zk` when the email is a Google account, and `email-zk` for every address. Both have the same effect: the login request may complete by waiting. Neither proof completes a login alone. Approval from a signed-in device or the full wait is still required.

- Proofs over email the user **receives**, including any email from the host, MUST NOT be accepted. The host holds its own DKIM key and keeps copies of what it sends, so it could make them.
- Providers that do not sign with an aligned RSA key of at least 2048 bits cannot produce `email-zk` proofs. Those users sign in with method `none`.
- **Method `none`** is a login without an email proof. It is allowed only in `approve` mode, and completes only by a device approval or the fast path, never by waiting.

Further OpenID Connect issuers MAY be added with their own circuit, when they sign a verified email claim and support app-owned redirects.

### Login request

The new device sends `{ identifier, method, emailProof }` to each holder named in the identifier (BRC-154 `POST /auth/complete`). Each holder:

1. **Verifies.** It checks that:
   - the identifier is signed by the pinned attester key, unexpired, and has purpose `login`;
   - its holders equal the enrolled holder set;
   - its `accountRef` matches the record;
   - the email proof passes the holder checks, if one is given.

   Any failure is a refusal.
2. **Opens a login request**, identified by its binding, so every holder knows it by the same id. `readyAt` is `now + waitSec` with an email proof, and never without one. A record has at most one open request; a new one replaces the old.
3. **Notifies** with a [BRC-33](../peer-to-peer/0033.md) message to the device authority key's messagebox. Every signed-in device watches that messagebox. The attester has already emailed the inbox.
4. **Answers:**

```json
{
  "binding": "<base64url>",
  "readyAt": <unix seconds> | null,
  "mode": "approve" | "wait",
  "recentDevices": [{ "label": "<text>", "lastSeen": <unix seconds> }]
}
```

`mode` is `approve` when at least one device is recent, and `wait` otherwise. A holder MUST refuse a request without an email proof when no device is recent and no fast-path signature is present.

The new device shows:
- **approve:** "Approve on MacBook · Desktop (seen 2 hours ago) or Pixel · Mobile", with the match number, and when the login will be ready anyway if nobody answers.
- **wait:** "None of your devices has been online in 7 days. You can sign in on Oct 16. Check your email in the meantime."

### Approving

A signed-in device that receives the notice, or finds the request at `GET /login/pending` (signed by its device authority key), MUST:

1. Verify the identifier's attester signature against its own pinned key.
2. Show `context`, and the match number as one of three two-digit choices. The other two are random and distinct. The user picks the number shown on the new device.
3. Refuse the request if the user picks a wrong number.

When the user picks correctly and confirms, the device sends each holder named in the identifier:

```json
POST /login/approve
{ "binding": "<base64url>", "signature": "<by the device authority key>" }
```

The signature covers `brc250-approve\n<binding>`. The holder sets `readyAt = now`.

Number matching means a user approving their own login cannot be tricked into approving an attacker's login started at the same moment. The attacker's login has a different number, and replaces the user's own request, which the user would notice.

### Refusing

`POST /login/refuse` to each holder, with either:
- `{ binding, signature }`, where the signature is by the device authority key over `brc250-refuse\n<binding>`; or
- `{ binding, refuseCode }`, where SHA-256 of the code is the identifier's `refuseHash`.

Signed-in devices send refusals to the holders directly. The inbox link opens a page that sends the refusal to each holder from the user's browser.

A holder MUST close the request at once. After a device refusal, it SHOULD refuse new login requests on the record for 24 hours. A refusal only delays a login, so it is safe to honour from the inbox link even if the inbox is not the owner's.

### Fast path

A login request that carries a signature by the record's fast key over `brc250-fast\n<binding>` is ready at once at that holder. The new device holds the offline slice, so it needs that many fewer holder shares to reach the threshold.

### Release

`POST /share/retrieve` with the binding:
- answers `425` with `readyAt` while the request is open and not ready;
- answers `410` once it is refused or replaced;
- otherwise returns the share sealed to `L` with [BRC-78](../peer-to-peer/0078.md).

A holder MUST NOT return the share in any other form. Once released, the request closes.

### Completing the login

The new device MUST:

1. Collect the threshold of shares and rebuild the vault master locally with BRC-140, checking the integrity hash.
2. Check that the master derives the record's device authority key, and discard the result if it does not.
3. Discard `L`.
4. Send its first presence, so it becomes a signed-in device.
5. Restore its accounts by [BRC-208](./0208.md) discovery.

Unlocking afterwards is local (password or biometrics). Email login is for adding a device, not for each session. Signing out wipes the vault from the device and sends a `signedOut` presence.

## Security considerations

| Attacker | What they have | Why they fail |
|---|---|---|
| The host (HandCash), or an insider | Signed identifiers, inbound mail, its own DKIM key | It cannot forge Google's signature or the user's provider's DKIM signature, so it cannot make an email proof. Its own DKIM key proves nothing, because only mail the user sends counts. An approval needs a signed-in device. It holds at most one share. A login it starts itself shows on every recent device. |
| One holder, or an insider | One share and an email commitment | Below threshold by construction. The commitment does not reveal the email. |
| All holders colluding | Every holder share | They still need an email proof or an approval. Choose holders run by independent operators. |
| A look-alike host | A fake HandCash page, a look-alike mail domain | Its key is not the pinned attester key. No token it obtains has HandCash's audience. Mail sent to its domain does not match the pinned `loginMailbox`. |
| A phishing site asking the user to "sign in with Google" | The user's Google sign-in | The code goes to the redirect of the app that opened the sign-in. A site or a remote attacker's app never receives a token for the user's browser session. |
| Someone collecting email the user sends them | DKIM-signed messages to the attacker | Not proofs. Only mail addressed to the pinned host mailbox, with this login's binding in the address, counts. |
| A phishing site asking the user to email `login+…@handcash.io` | An `email-zk` proof for a login the attacker started | That login must start inside the victim's HandCash account. It still needs a recent device to approve, or a seven-day wait. The victim's real inbox holds the attester's notice and refuse link the whole time. This path is easier to phish than `oauth-zk`, which is why neither proof completes a login alone. |
| An attacker signed in to their own HandCash account | Identifiers for their own account | Their `accountRef` points to their own record, never the victim's. |
| An attacker with the victim's HandCash session | Enroll identifiers for the victim's account | Replacing an existing record needs the record's device authority key, so they cannot swap in their own email. |
| Someone guessing emails | — | The salt is released only for a signed identifier for that account. |
| A remote attacker relaying the match number | An approval prompt on the owner's device | Their login must start inside the owner's HandCash account. It shows the attester-seen `context` on every recent device, and any refusal ends it. Users who approve a login they did not start are the one case no flow without a hardware factor can prevent. |
| Someone controlling the inbox | Valid email proofs of either kind | If the owner has a recent device, that device sees the request and refuses it. If not, the login waits seven days, and any device that comes online in that time, or the inbox link, can refuse. The residual risk is an owner with no device and no attention to the inbox for a full week. |
| A stolen signed-in device | The vault already | Approving adds nothing. Locked, it stops sending presence and drops out of `recentDevices` after seven days. |
| Google, or the user's mail provider | The ability to sign tokens or mail as the user | The same as the inbox: approval or a wait the owner can refuse. |
| A forged DKIM key via DNS | A fake `email-zk` proof | DNSSEC, or agreeing independent resolvers. |
| A replayed old proof | — | The binding includes a nonce, the account and the login key, and expires within 15 minutes. Google tokens expire within an hour. |

- **The wait is the safety, not a setting.** Holders MUST NOT release without a device approval, the fast-path signature, or a full seven-day wait with an email proof.
- **One approval is enough.** Any signed-in device already holds the wallet, so requiring every device adds no security. It would also lock out a user whose lost phone keeps reporting presence while unlocked.
- **Any one refusal wins.** A refusal never moves funds, so honouring the most cautious device is safe.
- **Circuit soundness.** The pinned circuits are part of the security. Each MUST be audited, and its trusted setup published, before holders accept it. A new circuit is a new manifest, pinned only by re-enrollment.

## Rationale

- **Why provider signatures and not a one-time code?** A code the operator sends is a code the operator can enter. DKIM and Google's token signature come from outside the wallet's operators.
- **Why any email, not only OAuth?** Every major provider DKIM-signs outgoing mail, so one sent email proves an address at any of them. OAuth alone would shut out everyone without a Google account.
- **How the host is validated.**
  - For `email-zk`, the recipient is inside the signed headers. The proof shows the mail went to the pinned mailbox at `handcash.io`.
  - For `oauth-zk`, Google records which app a token was issued to, and issues tokens for HandCash's client ids only to apps on `handcash.io`'s verified redirects.

  Either way the email is tied to the host without trusting the host's own word, and the pinned attester key ties the identifier to the same host.
- **Why the binding goes in the recipient address.** Every email the user ever sends carries a DKIM signature. If the binding could sit in a subject or body, an attacker could collect a proof from a message the user sent anywhere, for example an invoice number in a subject line. Requiring it in the `To` address on the host's own domain means only mail the user deliberately sends to HandCash, for this login, can count.
- **Why not a zero-knowledge proof over an email from handcash.io?** A message HandCash sent proves only that HandCash sent it. HandCash keeps a copy and holds the DKIM key, so it could produce that proof for any user without them. It would make HandCash a custodian.
- **Why neither proof is enough alone.** A user can still be talked into sending one email to the right address. Device approval and the waiting period, with the notice in the real inbox, are what make that phishing fail.
- **Why zero knowledge?** Holders verify the provider's signature, the host and the binding without ever seeing the email, the message or the token. A compromised holder leaks no email list.
- **Why pin the host and holders?** A login started through any other host, or naming other holders, is refused before anything else is checked. Phishing infrastructure cannot reach the holders.
- **Why bind to a login key?** Without it, any party that ever sees a valid proof could present it for its own device.
- **Why device approval, and why a wait without it?** An inbox can be stolen. A device the user already holds is the strongest second factor they can have, and it needs no passkey sync, PIN or authenticator. Users with no device left still get in. They just wait long enough that a theft would have been noticed.
- **Why presence?** It lets the new device say up front whether to look for an approval prompt or plan on the wait. It does not change what holders enforce.
- **Why HandCash as host?** Users already sign in to HandCash and the market with that account. Signing the identifier there ties a login to a real account and makes migration a step rather than a new login.

## Non-goals

- Session tokens for websites. Sites keep using [BRC-100](./0100.md) with the wallet.
- Spending authorization. Shares are released to rebuild the master, never to co-sign.
- Phone numbers, SMS or knowledge questions as proofs, or email the user receives.
