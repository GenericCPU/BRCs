# BRC-250: Email Login for BRC-140 Share Vaults

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

## Abstract

This standard lets a user add a new device to a self-custodial wallet by proving their email address, with no party able to take the wallet.

The wallet's vault master is split with [BRC-140](../key-derivation/0140.md). Independent [BRC-154](./0154.md) backup services, called holders, each keep one share.

A holder sends its share to a new device when two things are true:
- the device presents a zero-knowledge proof of the enrolled email, made through a pinned host;
- one of the user's existing devices approves, or seven days pass without a refusal.

## Overview

1. The new device creates a one-time **login key** and signs in to the **host** (`handcash.io`).
2. The host signs an **identifier** naming the account, the holders and the login key. Its hash is the **binding**. The host emails the user a notice with a refuse link.
3. The new device proves the email in zero knowledge, bound to the binding, in one of two ways:
   - **Any address (`email-zk`).** The user sends one email to `login+<binding>@handcash.io`.
   - **Google accounts (`oauth-zk`).** The user signs in with Google in the app.
4. Each holder opens a **login request** and alerts the user's signed-in devices.
5. A signed-in device seen in the last seven days approves or refuses. If none answers, the request waits seven days.
6. Each holder sends its share, sealed to the login key. The new device rebuilds the master.

**Release rule.** A holder releases its share for a request only when the following holds:

```
not refused AND (approved OR fastPath OR (emailProof AND now ≥ openedAt + waitSec))
```

| Party | Holds | Can | Cannot |
|---|---|---|---|
| User's mail provider or Google | Its signing keys | Sign the user's mail or ID tokens | Release anything by itself |
| Host | Attester key, inbound mail | Start a login for a signed-in account | Make an email proof; approve a login |
| Each holder | One share | Release that share under the rule | Reach the threshold |
| Signed-in device | The vault master | Approve or refuse a login | — |

## Terminology

| Term | Definition |
|---|---|
| Vault master | The secret being transferred, for example [BRC-157](../key-derivation/0157.md) entropy. |
| Signed-in device | An install that holds the vault master. |
| Host | The service the user signs in to. It publishes a manifest and runs the attester. |
| Attester key | The host key that signs identifiers. |
| Holder | A BRC-154 service holding one share. Holders MUST be run by independent operators. |
| Login key (`L`) | A secp256k1 key the new device creates for one login. |
| Binding | The base64url SHA-256 of an identifier's preimage, without padding. It identifies a login everywhere. |
| Device authority key | A key only signed-in devices can derive. It signs presence, approvals and refusals. |
| Fast key | A key derived from the user's offline share. Its signature makes a request ready at once. |
| Email commitment | A salted Poseidon hash of the email address. Holders store this, never the address. |

## Specification

### 1. Conventions

- **Signature:** a 64-byte compact secp256k1 ECDSA signature over SHA-256 of a UTF-8 message, in hex.
- **Public key:** compressed secp256k1, in hex.
- **`pack_n(s)`:** the UTF-8 bytes of `s`, right-padded with zero bytes to `31·n`, split into `n` big-endian BN254 field elements.
- **Poseidon:** circomlib Poseidon over BN254.
- **Email commitment:** `Poseidon(pack_9(lowercase(address)), salt)`, where `salt` is one field element.

Every signature in this standard:

| Name | Signer | Message |
|---|---|---|
| identifier | attester key | the identifier preimage (§5) |
| presence | device authority key | `brc250-presence\n<deviceId>\n<label>\n<state>\n<at>` |
| pending | device authority key | `brc250-pending\n<at>` |
| approve | device authority key | `brc250-approve\n<binding>` |
| refuse | device authority key | `brc250-refuse\n<binding>` |
| reenroll | the existing record's device authority key | `brc250-reenroll\n<binding>` |
| fast | fast key | `brc250-fast\n<binding>` |

Holders MUST refuse an `at` more than 300 seconds from their clock.

### 2. Host manifest

The host serves `https://<host>/.well-known/brc250.json`:

```json
{
  "v": 1,
  "attesterKey": "<public key>",
  "loginMailbox": { "localPart": "login", "domain": "handcash.io" },
  "googleClientIds": ["<native-app OAuth client id>"],
  "circuits": {
    "email-zk": { "id": "<hex SHA-256 of the Groth16 verifying key>", "url": "<verifying key>" },
    "oauth-zk": { "id": "<…>", "url": "<…>" }
  }
}
```

- The mail domain MUST accept mail for `<localPart>+<anything>@<domain>`.
- `googleClientIds` MUST be native-app clients, which Google redirects only to app-owned addresses.
- The wallet fetches the manifest over TLS at enrollment and pins it. A pinned manifest changes only by re-enrollment (§4).

### 3. Keys

- **Device authority key.** The [BRC-42](../key-derivation/0042.md) child of account 0's identity key for protocol `[2, "brc250 device"]`, key id `1`, counterparty `self`.
- **Fast key.** The private key `HMAC-SHA256(key = offline share string, data = "brc250-fast\n" + holder origin)`. One fast key per holder.
- **Login key.** Fresh for each login. It is discarded once the login completes or fails.

Each install also keeps a random `deviceId` and a label such as `MacBook · Desktop`.

### 4. Enrollment

The enrolling device:

1. Splits the vault master with BRC-140. It gives one share to each of at least two holders and keeps at least one share as an offline slice. The holders together MUST meet the threshold; no single holder may.
2. Picks a random `salt`, obtains an identifier with purpose `enroll` (§5), and makes an email proof for it (§6). This proves the address before it is stored.
3. Sends each holder `POST /share/enroll`:

```json
{
  "share": "<BRC-140 share>",
  "identifier": { },
  "method": "email-zk" | "oauth-zk",
  "emailProof": { "proof": { }, "publicSignals": [ ] },
  "salt": "<hex>",
  "deviceAuthorityKey": "<public key>",
  "fastKey": "<public key, optional>",
  "waitSec": 604800,
  "manifest": { },
  "holders": ["<origin>", "…"],
  "device": { "deviceId": "<hex>", "label": "<text>" },
  "reenrollSignature": "<required if a record exists>"
}
```

The holder MUST:
- verify the identifier (§5, purpose `enroll`) and the email proof (§6);
- require `waitSec ≥ 604800`;
- keep at most one record per `accountRef`. If a record exists, it requires the `reenroll` signature by that record's device authority key. A host session alone can never replace a record;
- store the share encrypted at rest, together with `accountRef`, the email commitment, `salt`, both keys, `waitSec`, the manifest, the holder set, and the device with `lastSeen = now`.

### 5. Identifier

The new device creates `L` and signs in to the host. The host MUST issue identifiers only for the signed-in account:

```json
{
  "v": 1,
  "purpose": "login" | "enroll",
  "accountRef": "<hex SHA-256 of \"brc250-account\\n\" + host account id>",
  "loginKey": "<L>",
  "holders": ["<origin>", "…"],
  "context": "<client type and approximate location, as the host saw them>",
  "refuseHash": "<hex SHA-256 of the refuse code>",
  "iat": 0,
  "exp": 0,
  "nonce": "<16 random bytes, hex>",
  "signature": "<identifier signature>"
}
```

The preimage is the following lines joined with `\n`. `holders` are sorted and joined with `,`. `context` has no line breaks and is at most 200 bytes. `exp − iat` MUST be at most 900 seconds.

```
brc250-identifier
v1
<purpose>
<accountRef>
<loginKey>
<holders>
<context>
<refuseHash>
<iat>
<exp>
<nonce>
```

A holder accepts an identifier only if all of these hold:
- its signature verifies under the pinned attester key;
- `now < exp`;
- its `holders` equal the enrolled holder set;
- for `login`, its `accountRef` matches a record.

The **match number** is `uint16(SHA-256("brc250-match\n" + binding)[0..2]) mod 100`, shown as two digits.

For every identifier, the host MUST email the account's address. The email states the `context` and the match number. It carries the refuse link, and its `Reply-To` is `<localPart>+<binding>@<domain>`.

### 6. Email proofs

Both methods are Groth16 proofs under the circuit the pinned manifest names. The device SHOULD prove locally and log `[email-login] prove done <N>ms`. A proving service MAY be used. It learns the address, but nothing it sees works outside this binding.

The salt comes from `POST /login/salt` with a `login` identifier. A holder MUST NOT reveal a salt otherwise, so addresses cannot be guessed against the commitment.

#### 6.1 `email-zk` (any address)

The user sends one email from the enrolled address to `<localPart>+<binding>@<domain>`, by replying to the host's notice or through a `mailto:` the app opens. Subject and body are ignored. The host keeps the raw message until `exp`, and the new device fetches it with its host session.

The circuit takes the signed header block and the salt as private inputs. It proves:
1. A `DKIM-Signature` with `a=rsa-sha256` verifies over the relaxed-canonicalized headers it signs, under a 2048-bit RSA modulus with Poseidon hash `dkimKeyHash`.
2. Its `d=` is `dkimDomain`, its `s=` is `selector`, and its `h=` includes `from` and `to`.
3. The `From` address's domain is `dkimDomain` or a subdomain of it.
4. The `To` header contains `toAddress`.
5. `emailCommitment` is the commitment of the `From` address.

Public signals: `dkimKeyHash`, `pack_9(dkimDomain)`, `pack_3(selector)`, `pack_9(toAddress)`, `emailCommitment`.

The holder MUST check:
- the proof, under the pinned `email-zk` circuit;
- that the key at `<selector>._domainkey.<dkimDomain>` hashes to `dkimKeyHash`, fetched over DNSSEC or from two independent DNS-over-HTTPS resolvers that agree;
- that `toAddress` equals `<localPart>+<binding>@<domain>` from the pinned manifest. This proves the host and freshness, because the binding did not exist before the identifier;
- that `emailCommitment` equals the record's.

#### 6.2 `oauth-zk` (Google accounts)

The new device obtains a Google ID token whose `nonce` is the binding:
- itself, by the authorization code flow with PKCE ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636));
- through a redirect only it can receive: loopback on desktop, a verified app link on mobile ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252));
- with a code verifier held in the process that holds `L`.

It MUST NOT use a web redirect, the device authorization flow, or a pasted token.

The circuit takes the token and the salt as private inputs. It proves:
1. The RS256 signature verifies under a modulus with Poseidon hash `googleKeyHash`.
2. `iss` is `https://accounts.google.com`, `email_verified` is `true`, and `aud`, `nonce` and `exp` equal the public signals.
3. `emailCommitment` is the commitment of the `email` claim.

Public signals: `googleKeyHash`, `pack_5(aud)`, `pack_2(nonce)`, `exp`, `emailCommitment`.

The holder MUST check:
- the proof, under the pinned `oauth-zk` circuit;
- that `googleKeyHash` matches a key in Google's JWKS that is current or retired within 24 hours;
- that `aud` is in the pinned `googleClientIds`;
- that `nonce` equals the binding;
- that `now < exp`;
- that `emailCommitment` equals the record's.

#### 6.3 Limits

- Holders MUST NOT accept proofs over mail the user receives. The host can produce those.
- Addresses whose provider does not sign with an aligned 2048-bit RSA key cannot use `email-zk`. Such users log in with method `none` (§7).
- More OpenID Connect issuers MAY be added, each with its own circuit, if they sign a verified email claim and redirect only to app-owned addresses.

### 7. Login

#### Presence

While unlocked and online, each signed-in device sends `POST /presence` to each holder, at least daily and at most hourly:

```json
{ "deviceId": "<hex>", "label": "<text>", "state": "active" | "signedOut", "at": 0, "signature": "<presence>" }
```

`at` MUST increase per device. A holder records `lastSeen`, and drops the device on `signedOut`. A device is **recent** if `now − lastSeen < 7 days`.

#### Request

The new device sends `POST /login/start` to each holder in the identifier:

```json
{
  "identifier": { },
  "method": "email-zk" | "oauth-zk" | "none",
  "emailProof": { },
  "fastSignature": "<optional>"
}
```

The holder verifies the identifier and the proof. It then opens a request keyed by the binding, replacing any open request for the record:

- `emailProof` is `true` when a valid proof is present;
- `fastPath` is `true` when a valid fast signature is present;
- `openedAt` is `now`.

It MUST refuse the request if there is no email proof, no fast signature and no recent device. It sends a [BRC-33](../peer-to-peer/0033.md) message to the device authority key's messagebox, and answers:

```json
{
  "binding": "<base64url>",
  "readyAt": 0,
  "mode": "approve" | "wait",
  "recentDevices": [{ "label": "<text>", "lastSeen": 0 }]
}
```

- `mode` is `approve` if any device is recent, otherwise `wait`.
- `readyAt` is `openedAt + waitSec` with an email proof, `now` on the fast path, and otherwise `null`.

The new device shows either "Approve on <device> (seen <time>)" with the match number, or "Ready on <date>".

#### Approve

A signed-in device finds requests through the messagebox or `GET /login/pending`, sent with a `pending` signature and `at`. It MUST:
1. verify the identifier under its own pinned attester key;
2. show `context` and three two-digit choices, one of them the match number;
3. send `refuse` if the user picks a wrong number.

On a correct pick and confirmation, it sends `POST /login/approve` with `{ binding, signature }` to each holder. The holder sets `approved`.

#### Refuse

`POST /login/refuse` carries `{ binding, signature }` from a device, or `{ binding, refuseCode }` from the inbox link. The holder sets `refused`. After a device refusal, it SHOULD refuse new requests for the record for 24 hours.

#### Release and completion

`POST /share/retrieve` with `{ binding }` answers:
- `425` with `readyAt` until the release rule holds;
- `410` if the request was refused or replaced;
- otherwise the share sealed to `L` with [BRC-78](../peer-to-peer/0078.md), after which the request closes.

The new device MUST:
1. rebuild the master with BRC-140 and check its integrity hash;
2. check that the master derives the record's device authority key, discarding it if not;
3. discard `L` and send its first presence;
4. restore its accounts by [BRC-208](./0208.md) discovery.

Later unlocks are local. Signing out wipes the vault and sends `signedOut`.

### 8. Holder endpoints

| Endpoint | Caller | Authorized by | Effect |
|---|---|---|---|
| `POST /share/enroll` | enrolling device | `enroll` identifier, email proof, `reenroll` signature if replacing | create or replace the record |
| `POST /presence` | signed-in device | `presence` signature | update `lastSeen` |
| `POST /login/salt` | new device | `login` identifier | return the salt |
| `POST /login/start` | new device | `login` identifier, plus an email proof or fast signature unless a device is recent | open a request |
| `GET /login/pending` | signed-in device | `pending` signature | return the open request |
| `POST /login/approve` | signed-in device | `approve` signature | set `approved` |
| `POST /login/refuse` | signed-in device or inbox link | `refuse` signature or refuse code | set `refused` |
| `POST /share/retrieve` | new device | the binding; the share is sealed to `L` | release under the rule |

`/share/enroll` and `/share/retrieve` are the BRC-154 endpoints, with the bodies above.

## Security considerations

| Attacker | Outcome |
|---|---|
| Host or insider | Cannot sign the user's mail or Google tokens, so it cannot make an email proof. It cannot approve. It holds at most one share. Any login it starts alerts every recent device. |
| One holder | Holds less than the threshold. Sees only a commitment. |
| All holders together | Still need a proof and the rule. Use independent operators. |
| Look-alike host | Wrong attester key, wrong mail domain, wrong token audience. Refused. |
| Someone collecting mail the user sends them | Not a proof: the binding must be in the `To` address at the pinned host. |
| Phishing for a Google sign-in | The code reaches only the app that opened it. |
| Phishing the user into emailing `login+…@handcash.io` | Requires the victim's host session. Still needs approval or seven days, with the notice and refuse link in the real inbox. |
| A host session for the victim's account | Cannot replace the record without the `reenroll` signature. |
| Email guessing | Salt released only for a signed `login` identifier. |
| Inbox takeover | Recent devices refuse. Without one, seven days during which any device or the inbox can refuse. Residual risk: no device and no attention to the inbox for seven days. |
| User approving a login they did not start | Not preventable without a hardware factor. Mitigated by `context` and number matching. |
| Stolen signed-in device | Already holds the vault. Locked, it stops being recent after seven days. |
| Forged DKIM key in DNS | DNSSEC or two agreeing resolvers. |
| Replay | The binding covers the nonce, account and `L`, and expires in 15 minutes. |

- `waitSec` is a security parameter. Holders MUST NOT shorten it.
- One approval suffices: any signed-in device already holds the vault. One refusal suffices: refusing never moves funds.
- The circuits are part of the trusted base. Each MUST be audited, and its trusted setup published, before holders accept it.

## Rationale

- **Provider signatures, not one-time codes.** A code the host sends, the host can enter. DKIM and Google signatures come from outside.
- **Any address.** Every major provider DKIM-signs outgoing mail. OAuth alone would exclude most users.
- **Binding in the recipient.** Every sent email carries a DKIM signature. Putting the binding in the `To` address at the host means only mail deliberately sent to the host, for this login, counts.
- **Not mail from the host.** The host keeps copies and holds its own DKIM key, so such a proof would make it a custodian.
- **Devices as the second factor.** Users nearly always have another device. It needs no passkey sync, PIN or authenticator, and users with none still get in after the wait.
- **Zero knowledge.** Holders check the signature, host and binding without seeing the address, so a breached holder leaks no email list.
