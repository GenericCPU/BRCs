# BRC-164: Output Identity Tags for BRC-100 Wallets

David Case (david.case@shruggr.cloud)

## Abstract

This specification defines a **tag convention** for [BRC-100](./0100.md): an output tag prefix `outid:` that carries a stable list key for a held output. Callers use it with ordinary `listOutputs` tag filters. It does not change the BRC-100 request or response shape, and it does not require special wallet storage behavior beyond normal tags.

## Motivation

Basket profiles and applications often need a stable handle for one wallet output — reload after restart, target a spend, correlate UI to storage — without scanning every row.

Stamping that handle as a normal, **queryable** tag under a dedicated prefix makes `listOutputs` the lookup API, without new BRC-100 fields or pseudo-tag peel paths. A namespaced prefix (`outid:`) is preferred over bare `id:` so the tag is visibly a held-output / row handle and is less likely to collide with informal “id” tags from other tools.

## Specification

### Tag form

This specification uses tags of the form:

```
outid:<key>
```

- The prefix is exactly `outid:` (lowercase, ASCII).
- `<key>` is a non-empty string chosen by the writer that stamps the tag (wallet or tool).
- Because reference BRC-100 clients commonly **trim and lowercase** tags before store and match, writers SHOULD use a case-insensitive alphabet for `<key>` (e.g. lowercase hex or decimal digits), and readers MUST treat tag equality as case-insensitive.

Tags beginning with `outid:` are used for this output list-key role.

### Meaning

- `outid:<key>` identifies a **held output row** for list and spend targeting inside that wallet storage.
- It is **not** a global asset id, token id, origin, outpoint, remittance field, or proof of ownership.
- Encoding of `<key>` is defined by the writer (e.g. decimal storage primary key, UUID). Only that writer must round-trip it.
- Uniqueness: `<key>` SHOULD be unique among that wallet’s held outputs (or a documented narrower scope such as per basket).
- Stability: for a given held row, `outid:` SHOULD remain stable for the life of that row (including unproven / unmined outputs if they are listable).

### Behavior

`outid:` is an ordinary BRC-100 output tag. No special `listOutputs` semantics, peel, inject, or foreign-tag overwrite is required of generic wallet storage.

Conforming **tools and wallets that adopt this profile** SHOULD:

1. Stamp `outid:<key>` on the output when the row is created or first taken into custody (same path as any other tag).
2. Query with a full `outid:<key>` tag via ordinary `tags` / `tagQueryMode`.
3. Treat `outid:` as their own list key vocabulary — not as token id, origin, or on-chain identity. Basket profiles that need those notions use their own tags (e.g. `bsv21:<tokenId>`, `origin:…`).

Applications MAY read `outid:<key>` from `listOutputs` (with `includeTags`) and reuse it in later filters or app state.

### Out of scope

- Changing BRC-100 method schemas or WalletWire encodings
- Basket names, token economics, or provenance proofs
- Requiring a particular key generation algorithm (UUID, counter, storage PK encoding, …)
- Mandating peel/inject or other non-tag storage paths in reference wallets

## Security considerations

- **Not authentication** — Knowing `outid:<key>` only helps address a row inside a wallet that already authorized `listOutputs` / spend for that basket.
- **Authority** — The tag is only as trustworthy as the storage that stamped it. Counterparty remittance is not a substitute for the holding wallet’s (or tool’s) own stamp.
- **Case folding** — Assume tags are lowercased in storage; do not put case-sensitive secrets in `<key>`.
