# BRC-247: BAP-Backed Issuer Attestation

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

This BRC defines how a [BRC-100](../wallet/0100.md) wallet attests 1Sat and 1Color issuances with its existing BAP identity. The issuance carries a MAP issuer tape and a SIGMA signature by the current BAP signing key, so a holder can prove which BAP identity issued it. No second identity hierarchy is introduced. Legacy BSV-21 JSON deploys can carry the same stamp.

## Motivation

[BRC-163](../tokens/0163.md) lets a BSV-21 deploy carry a Sigma signature by "the issuer's identity key", and [BRC-160](../tokens/0160.md) leaves issuer authenticity for 1Sat inscriptions to a separate specification. [1Color](../tokens/0162.md) and its wallet module [BRC-207](../wallet/0207.md) identify an asset by its deploy outpoint and define no identity system. None of them says which key speaks for an issuer or what happens when it is rotated. Signing with the BRC-100 root key puts it on chain, links every asset to it, and can never be rotated.

BAP already provides a portable identity with rotating signing keys, and 1Sat wallets already publish BAP `ID`, `ATTEST` and `ALIAS` records (BitCom `1BAPSuaPnfGnSBM3GLV9yhxUdYe4vGbdMT`) under one key tree. A separate issuer key root would compete with BAP and give users two identities to manage. This BRC uses BAP for "who I am" and adds a signed stamp for "what I issued." It is the BAP profile of the BRC-163 issuer attestation and the issuer authenticity BRC-160 defers.

## Specification

### Roles

| Thing | What it is |
|---|---|
| Root identity | BRC-100 identity key. Apps prove it with a [BRC-138](./0138.md) signature. |
| BRC-169 handle | A `$handle` claimed on the root key. |
| BAP identity | The on-chain identity under `[1, "sigma"]` / `identity-{N}`, with records in basket `bap`. |
| Issuer attestation | A MAP issuer tape and input-bound SIGMA signature on a 1Sat inscription or token deploy, by the current BAP signing key. Also called the stamp. |

Display names and profile data come from BAP `ALIAS`. Rotating or revoking signing authority is BAP key rotation and destruction.

### Derivation

BAP keys are [BRC-42](../key-derivation/0042.md) children of the wallet root, as live 1Sat and Yours wallets derive them:

- `protocolID`: `[1, "sigma"]`
- `keyID`: `identity-{N}`, where `N` is the BAP sequence
- `counterparty`: `self`
- `identity-0` is the BAP root: its address derives the BAP ID, and it signs only the first ID record and a revocation. Each higher `N` is the signing key after a rotation.

Before signing, a wallet MUST take the current `keyID` from the highest `seq:` ID record in basket `bap`. If it also stores the identity's ID chain elsewhere, such as a [BRC-248](./0248.md) package, it MUST merge both first, so it never signs with a key another app has rotated away.

### Basket

BAP records stay in basket `bap`; asset outputs stay in their usual baskets (`1sat`, the per-asset `p color` baskets of [BRC-207](../wallet/0207.md), `bsv21` for [BRC-163](../tokens/0163.md) holdings, …). Readers take the highest `seq:` tag in `bap` as the wallet's own current key, so `bap` MUST hold only the identity derived from the wallet's BRC-100 root. Records for an identity under any other master key, such as an imported issuer key, MUST go in a different basket. [BRC-248](./0248.md) §9 defines the tags.

### Asset attestation layout

| Asset | Where the stamp goes |
|---|---|
| 1Sat inscription | At the end of the inscription output |
| 1Color deploy ([BRC-162](../tokens/0162.md)) | In a separate stamp output of the deploy transaction |
| BSV-21 JSON deploy (`deploy+mint` or `deploy+auth`, [BRC-161](../tokens/0161.md)) | At the end of the deploy output |

A 1Sat inscription or BSV-21 JSON deploy output issued under BAP MAY end with:

```
OP_RETURN
  1PuQa7K62MiKCtssSLKy1kh56WWU7MtUR5
  SET
  issuer
  <BAP signing public key, compressed hex>
  bapId
  <bap-id>
  |
  SIGMA
  <BSM | BRC77>
  <BAP signing address>
  <signature>
  <vin>
```

A 1Color deploy issued under BAP MAY be accompanied by one stamp output in the same transaction:

```
OP_FALSE OP_RETURN
  1PuQa7K62MiKCtssSLKy1kh56WWU7MtUR5
  SET
  issuer
  <BAP signing public key, compressed hex>
  bapId
  <bap-id>
  deploy
  <SHA-256 of output 0's locking script, lowercase hex>
  |
  SIGMA
  <BSM | BRC77>
  <BAP signing address>
  <signature>
  <vin>
```

BRC-162 requires a 1Color deploy to be output 0, so the stamp output names it by position. The deploy output itself stays an ordinary 1Color prefix followed by its owner lock, which BRC-207 wallets manage as baseline custody; a tape after that lock would not be. The stamp output holds 0 satoshis, carries no token prefix, and MUST carry the MAP issuer tape. A verifier MUST check that `deploy` equals the SHA-256 of output 0's locking script and that output 0 is a 1Color deploy; otherwise the stamp asserts nothing. A transaction MUST NOT carry two stamp outputs.

The issuer metadata is a [MAP](https://github.com/rohenaz/map) `SET` tape, the Bitcom protocol 1Sat inscriptions already use for metadata. If the script already has an `OP_RETURN` section, the tape is appended after a `|`. MAP keys MUST NOT repeat, and a script MUST NOT carry two issuer tapes.

The signature is a [SIGMA](https://github.com/BitcoinSchema/sigma) tape with algorithm `BSM` or `BRC77`; verifiers MUST accept both. `vin` is the ASCII decimal index of a real input. SIGMA signers resolve `-1` to a concrete index before writing, as [1sat-sdk](https://github.com/b-open-io/1sat-sdk) does, so verifiers MUST reject a SIGMA `vin` of `-1`. As SIGMA defines, the signed message is `sha256(inputHash ‖ dataHash)`:

- `inputHash` is `sha256` of the outpoint spent by input `vin`: the 32 bytes of its txid in display order (as the hex is written, not reversed), followed by its output index as a 4-byte little-endian integer.
- `dataHash` is `sha256` of every chunk of the locking script before the `|` that introduces the SIGMA tape. On an inscription or JSON deploy it covers the envelope, the owner lock and the MAP issuer tape when present. On a 1Color stamp output it covers the MAP issuer tape, whose `deploy` hash commits to the deploy's id, amount, payload and owner lock.

A tag or `customInstructions` claim is not a proof. On an inscription or JSON deploy the MAP issuer tape is optional; 1sat-sdk writes the SIGMA tape alone. With a tape, the SIGMA signer MUST equal `issuer`. Without one, the issuer is the SIGMA signing address, and a wallet finds its BAP identity from a [BRC-248](./0248.md) package or the BAP `ID` records that name that address; an indexer's lookup is unproven. Either way, the signing key MUST have been an active BAP signing key for the identity when the asset was mined. BRC-248 defines that verdict from block heights and the offline package that proves it.

The issuer signature is the first SIGMA tape. Later signatures, such as the platform co-signature the 1Sat docs describe, sign over it and do not change the issuer.

A wallet that does not yet know the funding outpoint MUST NOT sign. It MAY write the unsigned tape and sign in a later step. A mined issuer tape with no valid SIGMA tape asserts nothing, and readers MUST ignore its `issuer` and `bapId`.

Input signatures commit to the outputs, so the stamp must be complete before any input is signed. A BRC-207 wallet selects funding after the requested outputs are fixed; an issuer stamping a 1Color deploy through it therefore supplies the `vin` input explicitly and keeps output order (`randomizeOutputs: false`).

A BSV-21 deploy stamped under this BRC satisfies the [BRC-163](../tokens/0163.md) issuer attestation, with the BAP signing key as the issuer key. A writer that sets the BRC-163 `issuer:<pubkeyHex>` filter tag MUST use the same key as the MAP `issuer`. Deploys that do not request BAP attestation keep the BRC-163 SIGMA signature ([BRC-77](./0077.md) or BSM) unchanged.

### Not a processing profile

The stamp is evidence for display, not a [BRC-162](../tokens/0162.md) wallet processing requirement. A deploy MUST NOT name this BRC in its `req` map: a required profile makes every wallet that does not implement it refuse the asset, and the stamp is optional (see [Unsigned issuance](#unsigned-issuance)). An `issuer` or `bapId` in a payload `ext` entry or a display field is a claim, not a stamp, and readers MUST NOT show it as the issuer.

### Earlier AIP signatures

The 1Sat docs ([Signing](https://docs.1satordinals.com/adding-metadata/signing), [Collection SubType](https://docs.1satordinals.com/adding-metadata/collections)) describe an earlier form, `| AIP <address> BITCOIN_ECDSA <signature> -1`, where `-1` means the whole output script is signed. It signs no input, so anyone can write the same script into another transaction and the signature still verifies. A verifier MAY show such a signer as an unbound claim, but MUST NOT treat it as a stamp under this BRC. Writers under this BRC use SIGMA.

### Collections

The 1Sat Collection SubType requires the collection record and its members to be signed by the same key. BAP signing keys rotate, so under this BRC a verifier SHOULD treat a member as signed by its collection's issuer when both stamps verify for the same BAP identity, with each key active when its asset was mined.

### Unsigned issuance

The stamp is optional. An asset may be worth holding for its content or its spendable value alone, whoever made it. A 1Sat inscription or token deploy without an issuer stamp is a valid asset, as [BRC-163](../tokens/0163.md) already says of unsigned deploys:

- A wallet MUST let the user issue without a stamp when they have no BAP identity, or choose not to use it, and MUST show the user that the asset will name no issuer.
- An unsigned issuance MUST NOT carry the issuer tape, a stamp output, an `issuer:` tag or an issuer field in `customInstructions`.
- A wallet MUST NOT fall back to signing with the BRC-100 root key, or any key that is not a current BAP signing key.
- Receivers MUST accept unsigned assets and show the issuer as unknown, not as a defect.

### Attributing a held asset

The stamp sits on the genesis output (1Sat) or in the deploy transaction (1Color, BSV-21). A later holder holds a different output, so a stamp alone says nothing about that output. A wallet MUST NOT show an issuer for a held output until the output is bound to the stamped issuance:

| Asset | Binding |
|---|---|
| 1Sat inscription | A complete [BRC-150](../tokens/0150.md) proof from the held output back to the stamped origin |
| 1Color or BSV-21 token | A [BRC-176](../tokens/0176.md) validity proof from the held output back to the stamped deploy, whose outpoint is the token id |

The proof carries the stamped transaction, including a 1Color stamp output, so a holder verifies the stamp and the [BRC-248](./0248.md) key verdict offline. If the binding is missing or does not verify, the issuer is unknown. An indexer's answer MAY be displayed only as unproven.

### Display key

BRC-163 keys display by `(issuer, tokenId)`; BRC-207 identifies an asset by its asset ID alone. Under BAP the signing key changes on rotation, so two deploys by one identity can name different keys. A wallet that has verified a stamp under this BRC SHOULD key display by `(bapId, tokenId)`, label the issuer with the BAP `ALIAS`, and keep the signing key as the evidence behind it. Assets with no verified stamp keep the BRC-163 key when a BRC-163 signature verifies, and otherwise the token id alone with no issuer.

### Relationship to BAP records

| Concern | Where it lives |
|---|---|
| Publish, rotate, revoke signing authority | BAP `ID` records in `bap` |
| Profile and display name | BAP `ALIAS` |
| Attribute attestations | BAP `ATTEST` |
| Asset issuer stamp | This BRC |
| Offline proof of the key chain and profile | [BRC-248](./0248.md) identity package |

### Non-goals

- A second identity key tree beside BAP, such as a `[0, "sigma identity"]` protocol ID.
- Changing BAP `ID`, `ALIAS` or `ATTEST` wire formats.
- Replacing the BRC-169 handle.
- Replacing [BRC-52](./0052.md) identity certificates.
- Delegating issuance by handing a child private key to another wallet.

## Rationale

**BAP rather than a BRC-52 certificate.** A BRC-52 certificate is a certifier's claim about a subject key, revealed selectively to chosen verifiers. It does not order a subject's key rotations on chain, so it cannot tell a holder whether a key spoke for the issuer at the height its asset was mined, and the asset would still need a key to sign with. BAP records are public, signed and ordered by block height, and 1Sat wallets already publish them. The two compose: a certifier MAY certify a BAP root address, and a [BRC-202](./0202.md) `did:key` names one key but not its successors.

**A BAP signing key rather than the root identity key.** The root key is the user's identity across every app. On chain it cannot be rotated, and every asset it signed would name it forever. A BAP signing key can be rotated, or the identity revoked, without disowning assets mined earlier.

**MAP for the issuer metadata.** MAP is the registered Bitcom protocol 1Sat inscriptions already use for metadata, and readers already parse it. A bare JSON push has no protocol prefix and would need its own parser rules.

**A separate output for 1Color.** BRC-207 manages a token output automatically only when its prefix is followed by an ordinary P2PKH lock. A tape after the lock would leave the issuer's own supply or minting authority outside managed custody. The 1Color payload cannot hold the stamp either: SIGMA signs the bytes before its tape, and a signature inside the payload would sign itself. A sibling output keeps the deploy a plain managed output; the input binding confines the stamp to one transaction, and its `deploy` hash fixes which output 0 it names, so nobody who controls that input can pair the stamp with a different deploy.

## Reference implementations

- [1sat-sdk](https://github.com/b-open-io/1sat-sdk): `packages/actions/src/identity/` and `packages/actions/src/signing/{bap,sigma,aip}.ts` implement BAP under `[1, "sigma"]` and the SIGMA tape; `packages/actions/src/apply/inscribeSigma.ts` binds it to a 2-sat anchor input.
- HandCash Desktop (`@handcash/wallet-ui`): `src/wallet/bapRecords.ts` (BAP keys and records) and `src/wallet/issuerMetadata.ts` (the issuer tape on the stamped output). The 1Color stamp output is not yet implemented.
