# BRC-247: BAP-Backed Issuer Attestation

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

This BRC defines how a [BRC-100](../wallet/0100.md) wallet attests 1Sat and BSV-21 issuances using its **existing BAP identity key tree**. It does **not** introduce a second identity hierarchy.

The wallet's BAP path is:

- `protocolID`: `[1, "sigma"]`
- `keyID`: `identity-{N}`

That tree already publishes BAP ID / ATTEST / ALIAS records (BitCom `1BAPSuaPnfGnSBM3GLV9yhxUdYe4vGbdMT`) into basket `bap`. This BRC only adds a VIN-bound SIGMA tail and a MAP issuer tape on asset outputs, signed by the **current BAP signing key**, so an inscription or token deploy can prove "this BAP identity issued this asset."

## Motivation

Issuers need asset-level attestation without putting the wallet root on chain. BAP already solves portable person/profile identity under one key hierarchy. A parallel persona root (for example `[0, "sigma identity"]`) would compete with BAP and confuse wallets.

So issuer attestation MUST compose with BAP: one identity tree, one Identity UX, BAP for "who I am," SIGMA tails for "what I issued."

## Specification

### Roles

| Thing | What it is |
|---|---|
| Root identity | BRC-100 identity key. Apps prove it with a [BRC-138](./0138.md) signature. |
| BRC-169 handle | A `$handle` claimed on the root key. |
| BAP identity | The on-chain person/profile layer under `[1, "sigma"]` / `identity-{N}` (basket `bap`). |
| Issuer attestation | A MAP issuer tape and VIN-bound SIGMA tail on a 1Sat / BSV-21 output, signed by the current BAP signing key. |

There is no separate "issuer persona" key root. Display names and profile data come from BAP ALIAS (or equivalent). Rotation and revocation of signing authority are BAP key rotation / identity lifecycle, not a second control-output protocol.

### Derivation (normative — BAP only)

BRC-42 path used by live 1Sat / Yours BAP wallets:

- `protocolID`: `[1, "sigma"]`
- `keyID`: `identity-{N}` where `N` is the active BAP sequence
- `identity-0` is the BAP ID source; higher `N` are signing keys after rotation

Wallets MUST resolve the current signing `keyID` from the BAP basket (highest live `seq:` ID record), the same way they do for BAP ATTEST / ALIAS. A wallet that also keeps the identity's ID chain elsewhere (for example, a stored [BRC-248](./0248.md) package) MUST merge it with the basket first, so it never signs with a key another app has already rotated away.

Wallets MUST NOT introduce a competing protocol id such as `[0, "sigma identity"]` for issuer attestation.

### Basket

BAP identity outputs remain in basket `bap`. Asset outputs stay in their normal baskets (`1sat`, `bsv21`, …). Issuer attestation does not create a parallel `sigma-<id>` identity basket.

Basket `bap` holds only the identity under the wallet's own BRC-100 key tree, because readers take its highest `seq:` as the wallet's current key. A wallet that also issues under another master key (an imported issuer key) MUST keep that identity's BAP records out of `bap`. HandCash uses basket `bap issuer`.

### Asset attestation layout

When a 1Sat inscription or BSV-21 deploy+auth output is issued under BAP, the locking script MAY end with:

```
OP_RETURN
  1PuQa7K62MiKCtssSLKy1kh56WWU7MtUR5
  SET
  issuer
  <BAP signing public key, compressed hex>
  bapId
  <bap-id>
  |
  SIGMA
  <BSM | BRC77>
  <BAP signing address>
  <signature>
  <vin>
```

The issuer metadata is a [MAP](https://github.com/rohenaz/map) `SET` tape, the Bitcom protocol 1Sat inscriptions already use for metadata. If the script already has an `OP_RETURN` section, the tape is joined with `|`. MAP keys MUST NOT repeat, and a script MUST NOT carry two issuer tapes.

The SIGMA tail is [SIGMA](https://github.com/BitcoinSchema/sigma) with algorithm `BSM` or `BRC77`. Verifiers MUST accept both. The VIN field is the ASCII decimal of a concrete input index, and `-1` MUST be refused. The signature covers the script in front of the `|` and commits to the outpoint at that input.

A tag or custom-instructions claim is not a proof. The SIGMA signer MUST equal `issuer`, and that key MUST be a BAP signing key for `bapId` that was active when the asset was mined. [BRC-248](./0248.md) defines that verdict from block heights, and the offline package that proves it.

If the funding input outpoint is not known, a wallet MUST NOT append a signature. It MAY stamp unsigned claims so a later step can sign.

[BRC-150](../tokens/0150.md) is not modified. Existing BSV-21 root [BRC-77](https://bsv.brc.dev) Sigma signing stays unless the output requests BAP-backed issuer attestation.

### Relationship to BAP records

| Concern | Where it lives |
|---|---|
| Publish / rotate / revoke signing authority | BAP ID records in `bap` |
| Profile / display name | BAP ALIAS |
| Attribute attestations | BAP ATTEST |
| Asset issuer stamp | This BRC (SIGMA tail on the asset) |
| Offline proof of the chain and profile | [BRC-248](./0248.md) identity package |

### Non-goals

- A second identity key tree beside BAP.
- Replacing BAP ID / ALIAS / ATTEST wire formats.
- Replacing the BRC-169 handle.
- Handing a child private key to another wallet as delegation.

## Implementation notes

- 1sat-sdk: `packages/actions/src/identity` and `signing/{bap,sigma,aip}` already implement BAP under `[1, "sigma"]` and SIGMA tape helpers for ordinals.
- HandCash: Identity UX MUST present one hierarchy (BAP). Issuer attestation is a capability of that identity, not a sibling "Sigma identity" product.

## Compatibility note

Earlier draft text proposed `[0, "sigma identity"]` personas and `sigma-<id>` baskets. That approach is withdrawn in favor of BAP composition above. Implementations that shipped the withdrawn path SHOULD migrate issuer stamps onto the BAP signing key and stop advertising a parallel persona root.
