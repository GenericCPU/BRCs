# BRC-158: Outpoint BEEF

David Case / b-open-io (david.case@shruggr.cloud)

## Abstract

This BRC defines Outpoint Background Evaluation Extended Format (Outpoint BEEF) Transactions, a variant of the BEEF transaction format (as defined in [BRC-62](./0062.md)) that focuses on atomicity—specifically, ensuring that all the data within a BEEF structure relates to a single "subject outpoint." This format disallows unrelated transactions within the BEEF structure, reinforcing a clear, minimalistic data set for outpoint-scoped validation while maintaining efficiency in bandwidth usage.

Outpoint BEEF is designed to solve problems arising from multiple graphs of unrelated transactions being aggregated into a single BEEF, which can complicate validation and increase data complexity. Outpoint BEEF introduces a strict structure optimized for single-outpoint use cases, ensuring that every transaction in the BEEF relates to a defined subject outpoint. This format is particularly suited for applications where the verification of a singular outpoint and its direct ancestry is critical—for example 1Sat tip→origin provenance ([BRC-150](../tokens/0150.md)).

## Motivation

The introduction of the BEEF format (BRC-62) provided a solution for transmitting transaction data in a binary format to allow [Simplified Payment Verification](./0067.md) (SPV) with minimal bandwidth. However, BEEF allows the inclusion of multiple, potentially unrelated transactions aggregated within the same structure, making it flexible but not ideal for cases where strict atomicity is needed.

[BRC-95](./0095.md) Atomic BEEF addresses atomicity for a **subject transaction**. Many protocols instead need atomicity for a **subject outpoint** (`txid` + `vout`)—the specific output being proven or transferred.

Outpoint BEEF is motivated by the following challenges:
1. **Outpoint Ambiguity**: Atomic BEEF names only a transaction. When the proven object is a particular output, the subject must include the output index.
2. **Simplified Use Cases**: Many use cases revolve around validating a single outpoint’s ancestry (e.g. a 1-sat tip), not an entire multi-output transaction graph in isolation from which output matters.
3. **Data Minimalism**: Limiting the BEEF to the dependency graph of the subject outpoint reduces unnecessary overhead.
4. **Streamlined Validation**: By restricting the BEEF to a single subject outpoint and its dependencies, validation has a clear expectation of the data's scope.

In response to these motivations, Outpoint BEEF introduces a header parallel to Atomic BEEF, with the subject extended from TXID to outpoint.

## Specification

Outpoint BEEF is an extension of BEEF (BRC-62) with specific structural and validation rules that ensure atomicity around a subject outpoint. It adheres to the same encoding and transaction structure principles as Atomic BEEF ([BRC-95](./0095.md)), with the following constraints:

### Header Structure

Outpoint BEEF starts with a constant prefix followed by the subject outpoint. That outpoint is the reference the entire BEEF structure must relate to.

- **Prefix**: The first 4 bytes of the Outpoint BEEF structure must be `0x16a7beef`, a fixed constant to indicate Outpoint BEEF.
- **Subject TXID**: The next 32 bytes are the TXID of the transaction that created the subject outpoint.
- **Subject vout**: The next 4 bytes are the output index (unsigned little-endian uint32) of the subject outpoint.

| Field           | Description                                                                                          | Size           |
|-----------------|------------------------------------------------------------------------------------------------------|----------------|
| Outpoint Prefix | Fixed constant `0x16a7beef`, indicates the start of an Outpoint BEEF structure                       | 4 bytes        |
| Subject TXID    | The TXID of the transaction that created the subject outpoint                                        | 32 bytes       |
| Subject vout    | The output index of the subject outpoint (uint32 LE)                                                 | 4 bytes        |

### Transaction Inclusion Rules

Outpoint BEEF strictly enforces that all transactions included in the structure must be part of the subject outpoint's dependency graph. This means that every transaction in the BEEF structure must either be:
1. The transaction that created the subject outpoint, or
2. An ancestor transaction required to validate the inputs of that transaction (recursively), as needed for the verification purpose for which the Outpoint BEEF is used.

Transactions that fall outside of this graph, or are unrelated, are not allowed in Outpoint BEEF. This ensures that the BEEF is entirely focused on a single, verifiable outpoint and its direct dependencies.

For 1Sat ordinal provenance specifically, required ancestors include source transactions needed to calculate the ordinal at each hop; see [BRC-150](../tokens/0150.md).

### Validation Process

The validation of an Outpoint BEEF structure follows these steps:

1. **Subject Outpoint Identification**:
    - Extract the subject outpoint (TXID + vout) from the header. If the BEEF structure does not include the subject transaction or if any unrelated transactions are present, the validation fails.

2. **Transaction Graph Validation**:
    - The BEEF structure must contain all transactions necessary to validate the subject outpoint's creating transaction, recursively including ancestor transactions up to the point where each input can be confirmed with a Merkle proof (and any additional ancestors required by the verification profile in use).
    - The structure must not contain any transactions that are not part of the subject outpoint's dependency graph.

3. **Merkle Proof Validation**:
    - As with the original BEEF format, any included transactions that have been mined must be accompanied by BSV Universal Merkle Path (BUMP) data to prove their inclusion in the longest chain of blocks.
    - The Merkle roots derived from the BUMP data are verified against the local header service.

4. **Final Validation**:
    - The final validation is complete when all necessary transactions (including script evaluations) and proofs have been processed, and the subject outpoint is confirmed to be valid based on its dependencies and the applicable profile (e.g. 1Sat tip→origin rules in [BRC-150](../tokens/0150.md)).

### Error Conditions

Outpoint BEEF introduces two specific error conditions that must cause validation to fail:
1. **Missing Subject Transaction**: If the BEEF structure does not include the transaction identified by the subject TXID in the header, validation fails.
2. **Unrelated Transactions**: If any transactions within the BEEF structure fall outside the dependency graph of the subject outpoint, validation fails.

These error conditions ensure that Outpoint BEEF maintains strict atomicity and avoids the ambiguity and complexity of unrelated transactions within the same structure.
